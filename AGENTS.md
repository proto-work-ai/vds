# shtorivdom — сайт салона штор на заказ

Отвечай пользователю по-русски.

Nx-монорепозиторий с одним продуктом — сайтом shtorivdom.ru (пошив штор,
жалюзи, карнизы; Москва и область).

## Приложения

- `apps/shtorivdom-site` — сайт на Angular 22 с пререндером
  (`outputMode: static`). Taiga UI 5.22 + Tailwind 4.
- `apps/shtorivdom-site/api/*.php` — отправка заявок с форм на почту.
  **PHP не трогаем без отдельной просьбы.**
- `apps/shtorivdom-storybook` — Storybook для `libs/ui/site-kit` и оставшихся
  общих компонентов. К сайту напрямую не относится.

## Библиотеки

- `libs/atlas/{core,form}` — общие утилиты и формы на Taiga UI.
- `libs/ui/site-kit` — компоненты и стили основного сайта.
- `libs/metadb/core`, `libs/fonts`.

## Правило архитектуры форм

- Общие поля и поведение выносить в переиспользуемый Angular-компонент только
  если формы действительно совпадают по структуре и сценарию.
- Если форма заметно отличается по полям, оформлению, валидации или поведению,
  создавать отдельный компонент (`DesignerLeadFormComponent`,
  `CalcLeadFormComponent`, `QuizLeadFormComponent` и т.п.), а не добавлять
  множество флагов и условий в общий компонент.
- Страница должна подключать форму одним понятным тегом компонента. Разметку
  `<form>`, поля, состояние отправки и блок успешного результата не дублировать
  в страницах.
- Перед созданием нового компонента проверить существующие формы и переиспользовать
  только стабильные части: сервис отправки, тип ответа API, валидацию и общие
  визуальные поля.

## Команды

```bash
npm run site:serve          # http://localhost:4200
npm run site:build          # продакшен-сборка
npm run site:start          # запустить собранный SSR-сервер
npm run storybook:serve     # http://localhost:4400
npm run sitemap             # sitemap.xml и robots.txt
```

## Грабли

- Версии Angular держать одинаковыми (~22.1.x) у всех `@angular/*`, иначе
  `npm install` падает на peer-зависимостях.
- Taiga UI зафиксирован на `5.22.0`: не использовать API из других версий.
- Цены — `model/price-list.service.ts` (`curtainPriceMap` по `key` страницы
  каталога). Цифры ориентировочные, ждут реального прайса.
- Шрифты: Lato 2.0 (`lato-font`, текст) и Playfair Display
  (`@fontsource/playfair-display`, заголовки), оба с кириллицей; подключены в
  `styles` в `project.json`. У Lato из Google Fonts кириллицы нет.
- Правила владельца — скилл `shtorivdom-owner-rules`.
- Для проверки API Taiga UI, контролов и иконок использовать Taiga UI MCP:
  https://github.com/taiga-family/taiga-ui-mcp
- Предупреждения NG8113 (импорт не используется в шаблоне) убирать сразу.

## Перенос на Angular

- При переносе из мокапов общие изменяемые данные сразу выносить в единый
  типизированный конфигурационный файл Angular. Цены, контакты, сроки и другие
  настройки нельзя дублировать в шаблонах страниц, компонентах и SEO-данных.
  Если значение используется в нескольких местах, источник правды создаётся
  до переноса разметки, а мокап и Angular получают значение из него или из
  общего генератора.
- При переносе макета или функциональности на сайт весь переносимый код
  переписывать на Angular: разметку — в шаблон компонента, состояние — в
  signals/модели, действия — в методы компонентов или директив, общие данные —
  в сервисы или типизированные входы. Не оставлять рядом отдельный JS с
  `querySelector`, ручной заменой HTML или глобальными обработчиками событий,
  если это поведение относится к Angular-компоненту.
- После переноса удалять ставший ненужным макетный JS и проверять сценарий в
  браузере, включая SSR и мобильный экран.
- При больших изменениях интерфейса или структуры обязательно сверять итоговый
  Angular-сайт с исходными макетами в `mockups/site/src`: состав и порядок полей,
  тексты, состояния, блоки и адаптивное поведение. Успешная сборка сама по себе
  не считается проверкой соответствия макету.
- Проверяемое описание переноса каждой страницы хранится в
  одноимённом файле рядом с исходником: `page.html` + `page.angular.md` (для генератора
  каталога — `catalog.mjs` + `catalog.angular.md`). При создании страницы сразу копировать
  `_template.angular.md`; без описания страница не считается созданной. При изменении
  структуры, формы, скролла, иконок либо интерактивности обновлять оба файла вместе.
  Изменение требований в `.angular.md` также должно быть отражено в HTML-мокапе до
  переноса в Angular. Общий индекс и чек-лист находятся в
  `mockups/site/src/pages/ANGULAR-PORTING.md`.
- Описание страницы писать с прицелом на реализацию в Angular: указывать дерево
  компонентов, переиспользуемые компоненты и директивы, inputs/outputs, signals или
  модели состояния, Reactive Forms, события, источники данных, SSR-ограничения и
  макетный JS, который при переносе нужно заменить Angular-логикой и удалить.
- При переносе делать минимальные изменения: сохранять структуру, порядок, тексты,
  размеры, отступы, цвета, иконки и пользовательскую механику мокапа. Менять способ
  реализации на Angular, но не перерабатывать дизайн и поведение без отдельной задачи.
- После переноса и генерации страниц проверять Tailwind-классы командой
  `npm run check:tailwind-classes`. Опечатки и неизвестные префиксы (`tetext-`,
  `texttext-`, `tex-[...]`) исправлять до сборки и визуальной проверки; произвольный
  класс дополнительно подтверждать по собранному CSS, потому что Tailwind молча
  игнорирует невалидные имена.
- В мокапах использовать те же иконки Taiga UI, что планируются в Angular. Иконку
  указывать в `.angular.md` как `@tui.<name>`, а в HTML вставлять SVG с тем же именем
  из установленного `@taiga-ui/icons`, сохраняя одинаковую геометрию.

## Правила разработки и переноса мокапов

- Разрабатывать интерфейс блоками: один самостоятельный визуальный блок мокапа
  должен становиться одним Angular-компонентом.
- Не переносить страницу целиком большим HTML-файлом и не вставлять интерактивный
  mockup-блок напрямую в страницу Angular.
- Структуру и визуальные состояния брать из мокапа, а состояние и действия
  переносить в TypeScript компонента или директиву.
- Данные блока описывать типизированными моделями и передавать через inputs;
  события отдавать через outputs. Контакты, цены, SEO и API не зашивать в шаблоны.
- Одинаковые блоки переиспользовать через общий компонент. Формы и блоки с разной
  логикой оформлять отдельными компонентами, не раздувать общий компонент флагами.
- Для каждого интерактивного блока проверять desktop, мобильный экран, клавиатуру,
  фокус, ошибки, загрузку, успешное состояние и SSR.
- После переноса удалять JS мокапа, который больше не используется Angular-версией.
- Переиспользуемые блоки держать в `libs/ui/site-kit`, страницы должны собирать
  их через понятные компоненты и конфигурацию.
- Для нового блока по возможности создавать комплект:
  `component.ts`, `component.html`, стили, типы данных и Storybook story.
- Сначала доводить блок до рабочего состояния в Angular, затем синхронизировать
  мокап и запускать сборку, lint и визуальную проверку маршрута.

## Правила интерфейса и форм

- Базовый размер обычного текста сайта и мокапов — `14px`. Более крупный размер
  задавать явно только заголовкам, акцентам и компонентам, где это предусмотрено макетом.
- Размеры текста в пикселях задавать только чётными значениями (`12px`, `14px`,
  `16px`, `18px` и далее), чтобы сохранять единую типографическую сетку.
- У каждого `tui-textfield` должен быть понятный `label`; обязательные поля
  помечать звёздочкой `*`.
- Во всех формах, где отображается поле имени, имя обязательно: поле должно иметь
  `required`, звёздочку `*` и участвовать в блокировке отправки невалидной формы.
- Во всех формах, где отображается город, он обязателен и оформляется с иконкой
  геолокации, `required`, звёздочкой `*` и состоянием ошибки внутри `tui-textfield`.
- Фон `input` и `textarea` — белый. Цвет label при фокусе должен соответствовать
  макету, текст не должен становиться невидимым.
- Не добавлять видимый border у `input` и `textarea`, если его нет в макете.
- После успешной отправки сохранять блок «Спасибо! Ваша заявка успешно отправлена!».
- Перед сдачей проверять форму в состояниях фокуса, ошибки, загрузки и успеха.
- `*appDefer` использовать только для телефонного поля с `tuiInputPhone`, где
  это требуется текущей инициализацией маски. Не добавлять `*appDefer` к имени,
  городу, комментарию или другим обычным полям.
- Для иконок в Taiga UI использовать штатные свойства контрола, например
  `iconStart="@tui.search"`, `iconStart="@tui.user"` или
  `iconStart="@tui.phone"` на `tui-textfield`. Не вставлять отдельный
  `<tui-icon>` внутрь поля, если иконка должна быть частью контрола.
- Перед добавлением иконки сверяться с API Taiga UI и доступными именами
  иконок, а после изменения проверять внешний вид и сборку.
- На мобильных экранах отзывы должны поддерживать свайпы пальцем.
- При изменении формы удалять старую разметку и дубли, включая старые labels,
  `field-label`, повторяющиеся form-блоки и ручную DOM-логику.

## Изменения и Git

- Если владелец дал команду продолжать или выполнить задачу, доводить весь
  согласованный объём до рабочего состояния за один проход: не останавливаться
  после промежуточного компонента и не ждать повторных команд на каждый шаг.
- После полного объёма обязательно выполнить сборку и сообщить, что осталось
  только если это действительно отдельная задача или блокирующее ограничение.
- Не создавать commit без отдельной команды владельца.
- Не выполнять merge, push или публикацию без отдельной команды владельца.
- Перед сдачей показывать изменённые файлы и результат проверки сборки.
- PHP API не изменять без отдельной просьбы; Angular использует существующий
  контракт `/api/lead.php`.

## Деплой и кеширование

- Деплой выполняется на Timeweb по FTP командой `npm run site:deploy`. Без
  отдельной команды владельца ничего на сервер не загружать.
- Перед реальной загрузкой обязательно выполнить `npm run site:build`, затем
  dry-run `node tools/deploy-site-ftp.mjs` и проверить список файлов. Реальная
  загрузка запускается только с `--upload` и `FTP_PASSWORD` в переменной
  окружения; пароль не писать в код, аргументы или логи.
- `tools/ftp-upload.mjs` сравнивает SHA-256 с серверным manifest и отправляет
  только новые и изменённые файлы. Ресурсы загружаются раньше HTML; HTML всегда
  публикуется последним, чтобы он не ссылался на ещё не загруженный bundle.
  Текущие HTML, `.htaccess` и корневые JS/CSS загружаются при каждом деплое,
  даже если manifest считает их неизменными: manifest может не совпасть с
  фактическим содержимым сервера после ручной или прерванной загрузки.
- Angular production-сборка использует `outputHashing: all`. В `.htaccess`
  HTML кешируется на сутки (`max-age=86400, must-revalidate`), остальные файлы
  без хеша должны перепроверяться браузером, а JS, CSS и шрифты с хешем могут
  кешироваться на год с `immutable`. Не заменять этот механизм периодической
  принудительной очисткой кеша и не добавлять service worker без отдельной
  задачи.
- После деплоя проверить заголовки главной страницы и одного хешированного
  ресурса: HTML должен иметь `max-age=86400, must-revalidate`, ресурс — долгий
  `max-age` и `immutable`. Затем открыть основные страницы и проверить, что нет
  ответов 404 на новые JS/CSS.
