# Правила владельца shtorivdom

Проект — сайт салона **штор на заказ** (shtorivdom.ru). Код достался от сайта
натяжных потолков; всё, что связывает с потолками, — мусор.

## Границы

- **PHP (`apps/shtorivdom-site/api/*.php`) не трогать**, пока владелец не попросит.
  Работаем только с фронтом.
- Сначала — чтобы всё **собиралось и запускалось** (`npm run site:serve`,
  `npm run storybook:serve`), потом улучшения.

## Как предлагать работу

- Когда вариантов несколько — **дать выбрать** через вопрос с вариантами
  (`request_user_input` с несколькими вариантами), если этот инструмент доступен;
  иначе задать один короткий вопрос обычным сообщением.
- Удаление файлов — после явного «да» владельца; выбранный в меню пункт
  «удалить» считается разрешением.

## Чистка кода

- Удалять мёртвый код: неиспользуемые компоненты, модули, страницы, данные.
- Удалять **неиспользуемые импорты**, включая пустые `import {} from '...'`,
  и лишнее в `imports: [...]` компонентов (предупреждения NG8113).
  Проверка: `npx tsc -p apps/shtorivdom-site/tsconfig.app.json --noEmit --noUnusedLocals`.
- Удалять **ненужные комментарии** в коде и шаблонах: закомментированный код,
  HTML-метки вида `<!--Footer-->`. Оставлять только комментарии, объясняющие «почему»,
  eslint-директивы и TODO.

## Именование

- Никаких потолков в именах: не `StretchCeiling*`, `ProductType` потолков,
  `STPriceGroup` и т.п. Имена — про шторы и каталог (`injectCatalog`,
  `injectCatalogItemByKey`, `curtainPriceMap`).
- Тексты интерфейса — про шторы («Вид штор», а не «Тип потолка»).
- Цели Яндекс.Метрики (`ym(..., 'reachGoal', '<id>')`) не переименовывать
  без владельца: id должен совпадать с настройкой счётчика. Функции-обёртки
  переименовывать можно.

## Цены

- При переносе мокапов сначала создавать единый типизированный источник общих
  настроек Angular. Цены, контакты, сроки и другие повторяемые значения не
  копировать в шаблоны и компоненты; мокапы и генерируемые Angular-страницы
  должны получать их из общей конфигурации или общего генератора.
- Пока нет реального прайса — таблица цен **по образцу прайса потолков**:
  `model/price-list.service.ts` (`curtainPriceMap` по `key` страницы каталога),
  таблица `price-list-brand-table`, с пометкой «цены ориентировочные».
  Цифры заменить, когда владелец пришлёт прайс.

## Шрифты

- **Playfair Display** — заголовки, **Lato** — текст и кнопки. Обязательно
  с **кириллицей**.
- Playfair Display — пакет `@fontsource/playfair-display` (подмножества
  `cyrillic` и `latin`). У Lato в Google Fonts / @fontsource кириллицы нет —
  брать **Lato 2.0** из npm-пакета `lato-font` (официальная 2.015, OFL).
  Подключение — массив `styles` в `apps/shtorivdom-site/project.json`,
  переменные `--default-font-family` и `--heading-font-family` в `styles.scss`.
- Неиспользуемые шрифты удалять.
- Базовый размер обычного текста сайта, мокапов и компонентов `site-kit` — `14px`.
  Более крупный текст задавать явно только по макету.
- Размеры текста в пикселях должны быть чётными (`12px`, `14px`, `16px`,
  `18px` и далее). Перед сдачей запускать `npm run check:tailwind-classes`;
  нечётные произвольные классы `text-[Npx]` считаются ошибкой.

## SEO

- У каждой страницы свои title и description (`data.seo` маршрута или
  конструктор страницы каталога), canonical ставит `provideSeo()`.
- После добавления страниц — `npm run sitemap`.

## Формы и телефонные поля

- Формы сайта переводить на Angular Reactive Forms (`FormGroup`, `FormControl`,
  `ReactiveFormsModule`) и отправлять заявки JSON-запросом в существующий
  `/api/lead.php`. PHP-контракт не менять без отдельной просьбы владельца.
- Каждая форма должна быть действительно реактивной: использовать
  `[formGroup]` и `formControlName` для всех полей, а не только читать DOM
  через `querySelector`/`elements` в момент submit. `ngModel` в этих формах
  не использовать.
- Для Taiga UI использовать нативные контролы внутри `<tui-textfield>`:
  `<input tuiInput ... />` и `<textarea tuiTextarea ...></textarea>`. Атрибут
  `tuiTextfield` на нативном `<input>` не использовать: в Taiga UI 5.22 он не
  подключает директиву ввода, из-за чего поле ломает раскладку и выталкивает
  `iconStart` за свои границы.
- Для телефона использовать `TuiInputPhone` из `@taiga-ui/kit` и директиву
  `tuiInputPhone` с маской, например `mask="+7 (###) ###-##-##"`.
  Самописный `formatPhone` не добавлять: маскирование выполняет Taiga UI,
  а значение напрямую связывается с `FormControl`.
- Согласие оформлять через Taiga UI `TuiCheckbox`/`tuiCheckbox`, а не через
  голый нативный checkbox. Для форм использовать `size="s"` и передавать
  состояние через `FormControl`; не добавлять `checked`, `accent-*` или
  ручные размеры вроде `size-4`. Кнопки существующих форм не менять без просьбы.
- Ответ API типизировать именованным интерфейсом (например, `LeadResponse`),
  а не оставлять повторяющийся inline-тип `{ok?: boolean; error?: string}`.
- Контактные данные сайта (телефон, email, Telegram, MAX и карта) хранить только в
  `app/site-contacts.ts`. В шаблонах
  использовать `data-contact-link="phone|email|telegram|max|map"`; не дублировать
  `tel:`, `mailto:` и внешние ссылки по страницам.
- В одном Angular-шаблоне каждая форма должна иметь уникальную template-ссылку:
  нельзя повторять `#lead` у нескольких форм. Использовать понятные имена
  (`#calcLead`, `#contactLead`, `#heroLead`, `#quizLead`) и связывать именно их
  с `[formGroup]`, например `[formGroup]="calcLead.form"`. Повторная ссылка может
  привязать нижнюю форму к `FormGroup` верхней и привести к подсветке чужих полей.
- После изменения нескольких форм проверить все `#...="leadForm"` и
  `[formGroup]="...form"` в конкретном шаблоне, а не только TypeScript-директиву.
  Для проверки поведения нажать каждую кнопку отдельно и убедиться, что
  `touched/dirty` меняются только у её формы.
- Для каждого телефонного поля с `tuiInputPhone` оборачивать
  `<tui-textfield>` директивой `*appDefer`, например:
  `<tui-textfield *appDefer [tuiTextfieldCleaner]="false">`.
  Компонент страницы должен импортировать `DeferDirective` из
  `app/components/defer.component`, иначе standalone-шаблон не соберётся.

## Форматирование и линтинг

- Для TypeScript/JavaScript использовать стиль PSB lint: ширина строки 100,
  без точек с запятой, одинарные кавычки, `quoteProps: "consistent"`,
  trailing commas в многострочных конструкциях и автоматическое определение
  перевода строк.
- Для Angular HTML использовать Angular-aware Prettier parser, игнорировать
  чувствительность HTML-пробелов и не добавлять trailing commas в шаблонах.
- Для CSS/SCSS применять Prettier через Stylelint; разрешать SCSS at-rules
  (`@mixin`, `@include`, `@if`, `@for`, `@use`, `@function` и связанные),
  не считать пустой источник ошибкой.
- Для форматирования всего репозитория использовать `npm run format`, а для
  проверки без изменений — `npm run format:check`. Эти команды используют
  корневой `.prettierignore`; не форматировать вручную только один файл,
  если задача касается всего проекта.
- Перед сдачей проверять форматирование и линт изменённых файлов, не меняя
  несвязанный код.

## Learnings

- Перед переносом изменений из другой рабочей копии сначала проверить `git status`
  целевой папки: в `shtorivdom.git` могут быть незакоммиченные изменения владельца,
  которые нельзя перезаписывать или откатывать.
- При исправлении формы сохранять существующую структуру и API-контракт; сначала
  проверить реальную привязку `FormGroupDirective` в браузере, потому что визуальная
  подсветка соседней формы может быть вызвана повторяющимся template reference,
  а не событием `submit`.
- Динамические карточки калькулятора создаются не Angular-шаблоном, а
  `initPage()` в `apps/shtorivdom-site/src/app/behavior/site-behavior.ts`.
  Источник данных — `#calc-data`, контейнер — `[data-calc-kinds]`. Если JSON на
  странице есть, но контейнер пуст, проверять момент запуска после lazy-навигации
  и гидрации; инициализацию нужно выполнять только после готового DOM (при
  необходимости — через два `requestAnimationFrame`), а не дублировать карточки
  в HTML вручную.

## Деплой Angular-сайта

- Не выполнять FTP-деплой без отдельной команды владельца. Команда на изменение
  кода, сборку или проверку сайта сама по себе не разрешает публикацию.
- Порядок проверки перед публикацией:
  1. `npm run site:build`;
  2. `node tools/deploy-site-ftp.mjs` без `--upload`;
  3. проверить, что в сборке и dry-run присутствует `.htaccess` и ожидаемые
     HTML/JS/CSS-файлы;
  4. только после разрешения запустить загрузку с `FTP_PASSWORD` и `--upload`.
- FTP manifest содержит SHA-256 и позволяет загружать только изменённые файлы.
  Не отключать сравнение manifest ради полной перезаливки без причины. HTML,
  `.htaccess` и корневые хешированные JS/CSS являются критическими и должны
  загружаться при каждом деплое: это восстанавливает файлы, если manifest
  разошёлся с сервером после ручной или прерванной загрузки.
- В `tools/ftp-upload.mjs` сначала публикуются ресурсы, а HTML — последним.
  Сохранять этот порядок: новый HTML не должен появиться раньше файлов, на
  которые он ссылается.
- Не возвращать копирование всех SVG из `@taiga-ui/icons`: в production assets
  должен попадать только список реально используемых и системных иконок из glob
  в `apps/shtorivdom-site/project.json`. При добавлении `@tui.*` обновлять этот
  список и проверять иконку в браузере.
- Обычный FTP-деплой исключает `assets/taiga-ui/icons/**`, потому что владелец
  загружает иконки вручную. Флаг `--with-taiga-icons` использовать только по
  отдельной команде владельца; при добавлении новой иконки явно сообщать, что её
  нужно синхронизировать на сервере.
- Значение FTP-параллельности по умолчанию — 12. Если Timeweb ограничивает число
  соединений, снижать его переменной `FTP_CONCURRENCY` для конкретного запуска.
- Механизм кеша задаёт `apps/shtorivdom-site/public/.htaccess`: HTML кешируется
  на сутки с `max-age=86400, must-revalidate`, файлы без хеша получают
  `no-cache`, а хешированные JS/CSS/шрифты — `max-age=31536000, immutable`.
  Angular production должен сохранять `outputHashing: all`.
- После загрузки проверить через `curl.exe -I` заголовки HTML и одного
  хешированного ресурса, затем открыть `/`, `/price`, `/catalog` и проверить
  отсутствие 404 у JS/CSS. Если хостинг не применил `.htaccess`, остановиться и
  исправить серверные заголовки, а не добавлять таймер очистки кеша в Angular.
- Service worker и периодическую принудительную перезагрузку не добавлять без
  отдельной задачи. При текущей схеме пользователь автоматически получает новую
  версию HTML не позднее чем через сутки; принудительное обновление страницы без
  кеша получает её сразу.

## Перевод макетов на Tailwind

- Оригиналы Figma переведены в `mockups/landing-N` (сами оригиналы удалены по решению владельца, восстановить — из git) — статичный HTML на
  Tailwind 4: без React и рантайма Figma, интерактив — на чистом JS.
- Сохранять **все анимации и цвета**: keyframes, появление при прокрутке, hover
  из JS-обработчиков. Тексты, картинки и порядок блоков не менять.
- Инструменты: `tools/mockups/snapshot.mjs` (снимок через Chrome/DevTools
  Protocol), `tools/mockups/to-tailwind.mjs` (конвертер).
- После перевода — проверка: сравнение оригинала и копии по вычисленным стилям
  и размерам, плюс просмотр в браузере.
- Все картинки и иконки макетов — на отдельных страницах-галереях: карточка с
  названием и текстом, по клику открывается полная версия.
- Работа в отдельной ветке. **Ничего не мержить без команды владельца.**

### Как устроен перевод (проверено на 9 сайтах)

- Переводы — `mockups/landing-N/index.html` (+ `app.js` с интерактивом), общие скрипты —
  `mockups/shared/`, галереи — `mockups/images/` и `icons/` (страницы в папках:
  сервер макетов открывает адреса со слешем, относительные пути считаются от папки).
- Конвейер на сайт: `snapshot.mjs` (DOM до/после прокрутки) → `hover.mjs` (hover из JS) →
  `timeline.mjs` (слайдеры, вступления, текст по времени) → `scrollmap.mjs` (параллакс) →
  `to-tailwind.mjs` (флаги --hover --timeline --scroll --script app.js) → `gallery.mjs`.
- **Приоритеты как в оригинале:** инлайн-стили → утилиты `[prop:value]` БЕЗ `!`; свой CSS
  сайта и `<style>` из разметки → `@layer components`; `@layer base` сайта переносится
  (цвет текста/границ shadcn); токены темы из скомпилированных утилит → `@theme`.
  С `!` утилиты перебивали `!important`-правила сайта для телефона (важное из слоя сильнее
  важного вне слоёв).
- **Грабли:** `@import` внутри `@layer` или обрезанный по первой `;` адрес Google Fonts
  ломает сборку Tailwind целиком — страница без стилей; минифицированный `@import"…"` без пробела;
  `@property`/`@font-face` — только на верхнем уровне; токен темы, ссылающийся сам на себя,
  обнуляет цвет; появление framer-motion при прокрутке похоже на параллакс, но всегда приходит к
  нулевому сдвигу.
- В `app.js`: данные слайдов — из кода оригинала; классы, появляющиеся по действию, прогревать
  скрытым элементом; `const` не поднимается (TDZ); после `cloneNode` держать ссылку на новый узел.
- **Проверка обязательна:** `check-karina.mjs` / свой check-скрипт (каждое взаимодействие, ошибки скрипта через
  Page.addScriptToEvaluateOnNewDocument), `visual.mjs` (попиксельно, склейки jpg смотреть глазами),
  `compare.mjs` (вычисленные стили, пары по подписям), `matched-styles.mjs` — какое правило
  победило. Отличия от бесконечных анимаций, случайных частиц и кадров слайдеров допустимы.

## Прототип сайта (mockups/site)

- Сайт сначала живёт макетом: `mockups/site/` (http://localhost:4320/site/). Лендинги
  `mockups/landing-N` — **источники блоков**, их не меняем: нужный блок копируем в прототип
  и приводим к единому стилю (тёмно-синий `#0d223d` от логотипа, золото, крем;
  Playfair Display + Lato), анимации переносим вместе с блоком.
- Перед любой визуальной правкой Angular-сайта сначала находить соответствующий элемент
  в исходниках `mockups/site/src` и сверять точные цвет, размер, отступы, порядок и состав
  элементов. После изменения обязательно сравнивать результат с макетом визуально;
  успешная сборка не заменяет эту проверку.
- При переносе блока из мокапа в рабочий Angular-сайт обязательно делать отдельный
  Angular-компонент, а не вставлять большой HTML-блок прямо в страницу. Логику
  интерактивности переносить в TypeScript компонента, разметку — в его шаблон;
  например, квиз и калькулятор оформлены отдельными `QuizComponent` и `CalcComponent`.
- Для кнопки сброса квиза нужно сбрасывать всё состояние: ответы, текущий шаг,
  выбранные native radio-кнопки и поля формы заявки. После сброса показывать первый
  вопрос и плавно прокручивать к началу блока квиза с отступом под фиксированную шапку;
  не оставлять пользователя внизу страницы возле формы.
- Контент — **только с текущего сайта** `apps/shtorivdom-site` (тексты модулей, `catalog.data.ts`,
  `price-list.service.ts`, `contacts.ts`, SEO из `app.routes.ts`). Ничего не придумывать:
  чего нет (отзывы, фото работ) — заглушка с пометкой. Расхождения на текущем сайте
  (график, цифры «лет/изделий», чужие названия) — не исправлять молча, спросить владельца.
- Сборка: исходники в `mockups/site/src/` (partials: тема, шапка, подвал, форма; pages),
  `node tools/mockups/site-gen-pages.mjs` (цены и тексты политики из исходников сайта) →
  `node tools/mockups/site-build.mjs` (собирает `mockups/site/**/index.html`, логотипы инлайн).
  Готовые `index.html` руками не править.
